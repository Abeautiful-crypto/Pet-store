# 02 · 后端约束（Go）

> 当写后端代码、加接口、改状态机、处理名额/支付/取消/退款时遵循本文件。前端相关见 `frontend/*.md`，通用原则见 `general/principles.md`。

## 0. 前提假设

| 项 | 假设 |
| --- | --- |
| 后端语言 | **Go 1.22**（沿用参考范本；落地前确认） |
| 存储 | **MySQL 8.0+ 真相源 + Redis 7+ 缓存/去重**（沿用参考范本，详见 `backend/tech-stack.md`）；演示原型期可用内存态回退 |
| 金额单位 | **整数"分"（`int64`）**，本项目预约款固定 **9900 分 = 服务全款**，全程禁浮点 |
| 基础设定 | 1 家门店、1 个洗护项目、**3 个未来时段**、每时段容量 **3**、占位 **5 分钟**、取消分界 **2 小时** |
| 需求锚点 | SRS V1.0 + 题目原文 8 条规则 + 5 个必演场景 + 状态机迁移矩阵 |

## 1. 工程结构

```
cmd/                       # 入口（main）
internal/
  domain/ 或 model/        # 预约/时段/支付单/退款单/取消申请/服务记录 与状态机
  store/                   # 数据访问（名额原子更新、CAS、唯一约束、事务）
  service/                 # 业务编排（预约、支付、取消、退款、核销、履约、日清）
  api/                     # HTTP 接口 + 门店归属/角色越权校验
  cache/                   # Redis 名额读缓存、支付去重、会话
  app/                     # 配置与启动装配
pkg/                       # 可复用工具（money、idgen）
```

- 包名全小写、单数；文件驼峰；一个文件一个职责。
- 领域层不依赖存储层（依赖倒置），**状态机逻辑集中在一处**，禁止散落 `if status ==`。
- **所有角色读写同一条 appointment 记录**；状态变更只有一个写入点（乐观锁 `version`）。

## 2. 关键编码铁律（本题专属，违反即打回）

| 铁律 | 要求 | 反例（禁止） |
| --- | --- | --- |
| 金额 | 一律 `int64` 分，固定 9900；禁止 `float`/`double` | `price float64`、`9900/100` 参与运算 |
| 名额占用 | 原子条件更新：`UPDATE slot SET occupied=occupied+1 WHERE id=? AND occupied<capacity`；以影响行数判定成败 | 先 `SELECT` 再 `UPDATE` |
| 时段可约 | 创建预约前校验 `now < start_at` 且名额充足；已开始或已满直接拒绝 | 时段开始后仍允许下单 |
| 唯一有效预约 | 同一 `pet_id + slot_id` 只允许一条有效预约（待支付占位/已确认/取消审核中/已核销/服务中） | 重复预约重复占名额 |
| 5 分钟占位 | 未付款预约占名额 5 分钟，`pay_deadline_at` 到点即关闭并释放名额；释放**一次性** | 超时后名额不释放 / 重复释放 |
| 2 小时取消线 | `start_at - now >= 2h` 自动受理全额退款；`< 2h` 必须填原因转客服审核；等于 2h 走自动分支 | 只看"是否付款"决定取消方式 |
| 待审核门禁 | 取消审核中：名额保持、**禁止核销**，客服批准/拒绝才推进 | 审核期间前台可核销 |
| 幂等-支付 | `notify_key` / 渠道交易号唯一；重复通知只记流水、不改状态、不重复确认 | 同通知二次收款 / 二次记收入 |
| 迟到支付回调 | 预约已关闭后才收到支付成功 → 登记异常 + 退还款项，**不恢复预约、不恢复名额** | 复活已关闭预约 |
| 取消获准 | 不得再到店核销；名额仅释放一次 | 退款失败后名额可重新占用 |
| 退款状态独立 | 退款单状态独立可查（待退款/退款中/成功/失败待跟进），失败可重试；**不改变已取消终态** | 退款失败回滚预约状态 |
| 核销准入 | 前台只能核销 **本店 + 已确认 + 无待处理取消申请** 的预约；三条件任一不满足即拒绝且记录不变 | 只看已确认就放行 |
| 门店归属 | 校验操作者门店与 `appointment.store_id`；非本店员工操作拦截且不改动记录 | 内部构造身份绕过鉴权 |
| 取消×核销互斥 | 并发时谁先 CAS 成功谁赢，输方收明确失败；**唯一合法结果**，冲突留痕 | 两边都成功 |
| 终态门禁 | 已核销 / 服务中 / 已完成不能再走取消退款流程 | 已到店仍可退款 |
| 服务进度幂等 | `verify_at` / `started_at` / `finished_at` 顺序递进且只写一次；完成时收入只记一次 | 重复核销/完成重复记收入 |
| 未到店 | 时段结束后仍未核销，由店长标记并**写明原因**；本题约定**不自动退款**；不实现争议裁决 | 自动退款 / 加申诉入口 |
| 收入口径 | 已完成服务收入**只认已完成服务记录**；已收款 ≠ 收入 | 把 4 笔已付款（39600）全计作收入（应 9900） |
| 流水不可变 | 支付/退款/核销/异常均落**只增不改**的流水表 | 改历史流水"抹掉"异常 |
| 时间 | 所有"开始前 / 已开始 / 时段结束"判定用**服务端时间**，不信任客户端 | 客户端传 `expireAt` |

> 前端的"金额展示换算"与"越权渲染拦截"见 `frontend/code-style.md` / `frontend/permission.md`；后端这里是数据与接口的真相源。

## 3. 命名 / 注释 / 日志

- 状态值用常量（`StatusPendingPay` / `StatusConfirmed` / `StatusCancelReview` …），禁止魔法字符串。
- 公共函数写 Go doc；**状态机迁移处必须注释"对应题目规则第几条 / SRS 第几节"**。
- 日志结构化（key=value），关键动作打印：动作、预约号、前后状态、名额前后值、渠道交易号、操作者门店。

## 4. 并发

- 正确性靠**数据库约束 + 事务**保证，不靠应用层内存锁"猜"。
- 并发抢占（多人抢最后 1 个名额）用 goroutine + `sync.WaitGroup` 起压，断言最终不超卖且只有 1 人成功。
- 取消与核销并发用**同一状态写入点 + 乐观锁 `version`**，只允许一个结果生效。
- 所有共享状态访问走 `store`，不得绕开。

## 5. 静态检查（提交前必过）

- `gofmt` / `go vet` / `golangci-lint` 零告警。
- 编译通过、单测通过（见 `general/acceptance.md`）、覆盖率 ≥85%（见 `general/unit-test.md`）。

## 6. 后端一页速查

1. 这次改动对应状态机哪条迁移？——没有就不做。
2. 金额 9900 分 `int64`？名额原子条件更新？——不是就打回。
3. 5 分钟占位 / 2 小时取消线 / 迟到回调不复活 / 退款失败不复活——都守住？
4. 取消与核销并发只有一个合法结果？终态禁入取消？
5. 收入只认已完成服务记录？——把已付款全算成收入即违规。
