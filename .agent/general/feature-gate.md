# 08 · 逐功能点测试闸门（新增规则一）

> **用户追加规则原文**：「AI 在开发完一个功能点后，要去测试这个功能点有没有问题，没问题了之后才能继续进行下一阶段的开发」。
> **定位**：把 `general/principles.md` 第 2 节的"完成即测"从原则升级为**可检查、留证据、卡进度**的硬闸门。
> **配套**：`workflow/feature-points.md`（功能点清单）、`workflow/progress.md`（进度）、`workflow/gate-records/`（证据）、`general/unit-test.md`（单测要求）。

## 1. 一句话规则

**AI 开发完一个功能点后，必须立刻测试这个功能点有没有问题；测试结果 `PASS` 之前，禁止进入下一阶段、禁止开始下一个功能点。**

这不是"最后统一跑一遍 `go test`"，而是**每个功能点各自跑一次闸门**，且闸门结果落盘留证。

## 2. 功能点状态机

| 状态 | 含义 | 允许的动作 |
| --- | --- | --- |
| `未开始` | 清单中待开发 | 取该点（须前置功能点全部 `已通过`） |
| `开发中` | 正在写实现与单测 | 只允许改本功能点涉及的模块 |
| `待验证` | 代码写完，尚未跑闸门 | **只能跑闸门**，不得开新功能点 |
| `闸门失败` | 测试未通过 | 写 `issue-log` → 只修本点 → 回到 `待验证` |
| `已通过` | 闸门 `PASS` 且证据落盘 | 更新 `progress.md`、提交，然后才能取下一个功能点 |

合法迁移：`未开始 → 开发中 → 待验证 → (闸门失败 → 待验证)* → 已通过`。
**禁止**：`待验证 → 开发中(下一个功能点)`、`闸门失败 → 已通过`、`未开始 → 已通过`。

## 3. 闸门检查项（缺一即 FAIL）

| # | 检查项 | 判定方式 |
| --- | --- | --- |
| S1 | 前置功能点全部 `已通过` | 读 `workflow/gate-records/<前置ID>.json` 的 `result == PASS` |
| S2 | 本功能点涉及的每个模块都有单元测试 | 逐包检查 `*_test.go` 存在且非空；前端按 `unit-test.md` 第 5 节等价要求 |
| S3 | 该功能点的专项测试文件存在 | `workflow/feature-points.md` 中"必写单测"列逐个核对 |
| S4 | 格式与静态检查 | `gofmt -l` 无输出；`go vet ./...` 退出码 0 |
| S5 | 功能点测试通过 | `go test -race -count=1 -run '<该点正则>' <模块包>` 退出码 0，且**至少命中 1 个测试**（"0 tests ran" 视为 FAIL） |
| S6 | 场景断言 | 该点对应的 `general/acceptance.md` 场景断言逐条 PASS（含原型点击 / HTTP 验收） |
| S7 | 证据落盘 | 写 `workflow/gate-records/<ID>.json`：时间、功能点、命令、退出码、输出摘要 |

> 阶段 5 的交付点额外要求：覆盖率门禁 + 五大场景一键验收 + 全量回归（见 `workflow/feature-points.md`）。

## 4. 闸门命令（项目落地代码后执行）

```bash
gofmt -l .                                  # 必须无输出
go vet ./...                                # 退出码 0
go test -race -count=1 -run '<本功能点正则>' ./internal/<模块>   # 必须命中并全绿
python scripts/acceptance_check.py           # 涉及场景的功能点（服务已启动时）
```

> 项目当前处于**需求 + 原型阶段，尚无 Go 代码**：此时闸门以"需求/原型交付物"为对象——检查该页面/文档对应的 FR、场景断言、状态机迁移是否齐备且自洽，并把检查结论按第 5 节格式写入证据文件。**不得因为"还没有代码"就跳过闸门或把状态直接写成已通过。**

## 5. 证据格式（AI 每次闸门后写入 `workflow/gate-records/<ID>.json`）

```json
{
  "feature": "F3.1",
  "result": "PASS",
  "at": "2026-11-13T10:20:00+08:00",
  "checks": [{"name": "unit_tests", "cmd": "go test -race -count=1 -run ...", "exit": 0}],
  "tests_hit": 12,
  "requires": ["F2.1"],
  "notes": "前置 F2.1 已通过；无遗留 FAIL"
}
```

**"已测过"只认这个文件**。口头说"我测过了""应该没问题"一律不算；`progress.md` 的状态必须与证据一致。

## 6. 失败处理（强制顺序）

1. 闸门 `FAIL` → **立刻停止**，不碰下一个功能点的任何文件。
2. 按 `general/issue-log.md` 模板追加一条：现象、复现步骤、根因、解决、是否上升为约束、关联需求/状态机迁移。
3. 只修本功能点的问题；若暴露规则漏洞，同步补进 `backend/constraints.md` / 前端约束文件。
4. **原功能点重跑闸门**，直到 `PASS`。禁止用"改断言""跳过依赖""注释测试""调低阈值"换绿灯。
5. 回填 issue-log 的"解决"字段。

## 7. 明确禁止（违反即本次交付作废）

| 禁止行为 | 为什么 |
| --- | --- |
| 写完 3 个功能点再一起测 | 违反闭环优先，失败时无法定位是哪个改动引入 |
| 测试没过就说"已完成/已通过" | `principles.md` 第 1 节"不伪造结果" |
| 用"跳过依赖 / 跳过测试"绕过闸门 | 闸门失去意义 |
| 只跑 `go build` 当测试通过 | 编译 ≠ 功能正确 |
| 拼一个不存在的 `-run` 正则制造 "0 tests PASS" | 0 命中即 FAIL |
| 闸门失败期间顺手改别的模块 | 污染定位且扩大范围 |

## 8. 与既有文件的分工

| 文件 | 管什么 |
| --- | --- |
| `general/principles.md` | 总纲：闭环优先、增量开发、不伪造结果（原则层） |
| **本文件 `feature-gate.md`** | **逐功能点的状态机、检查项、证据、失败处理（执行层）** |
| `general/unit-test.md` | 哪些模块必须有单测、怎么写、必须覆盖哪些不变量 |
| `general/acceptance.md` | 提交前通用门槛 + 5 个必演场景断言 |
| `workflow/feature-points.md` | 功能点顺序、正则、断言、前置依赖 |
