# 09 · 模块单元测试强制规范（新增规则二）

> **用户追加规则原文**：「开发的模块要有单元测试」。
> **定位**：把这条要求落成**逐模块可检查**的规则；没有 `*_test.go`（或前端等价断言）的模块，功能点闸门直接 FAIL。
> **配套**：`general/feature-gate.md` S2 检查项、`workflow/feature-points.md` 的"必写单测"列。

## 1. 一句话规则

**每个被开发的模块都必须有单元测试；没有 `*_test.go`（或前端等价断言）的模块，功能点闸门直接 FAIL，不允许"先写实现、测试以后补"。**

## 2. 模块清单与对应测试文件（落地代码时的工程结构约定）

| 模块包 | 职责 | 必须存在的测试文件 | 至少覆盖的不变量 |
| --- | --- | --- | --- |
| `internal/model` | 预约实体、时段、支付/退款单、预约状态机 | `model_test.go`、`state_machine_test.go` | 合法/非法迁移、终态不可再改、金额 9900 分 |
| `internal/store` | `StateStore` 接口、MySQL 真相源、内存回退、名额原子更新、写失效 | `store_test.go`、`mysql_test.go` | 名额条件更新不超卖、CAS 关闭、唯一索引、事务回滚、缓存写失效 |
| `internal/cache` | Redis 名额读缓存 / 支付去重 / 会话 / 降级 | `cache_test.go` | Cache-Aside 写失效、`SETNX` TTL、Redis 不可用降级 |
| `internal/service` | 8 条业务规则唯一落点（预约、支付、取消、退款、核销、履约、未到店、日清） | `appointment_test.go`、`payment_test.go`、`cancel_test.go`、`refund_test.go`、`reception_test.go`、`settlement_test.go` | 见第 4 节必测不变量矩阵 |
| `internal/api` | REST/JSON、身份解析、五角色权限、错误码、回调幂等 | `server_test.go`、`permission_test.go` | 非本店员工拦截、越权 403、重复支付通知、迟到回调 |
| `internal/app` | 配置解析、启动装配、生产守卫 | `app_test.go` | 生产模式拒绝内存存储、必需配置缺失报错 |
| `web/`（前端） | 15 个角色页面原型（用户/前台/客服/店长/渠道） | **等价要求见第 5 节** | 四模块页面、requireRole、越权演示、状态色徽章 |

> 豁免：`main.go`（仅入口装配）、`migrations/*.sql`（DDL）、`docs/`、纯生成文件。豁免清单**只允许这一条**，新增模块一律纳入检查。

## 3. 单元测试写法

| 规则 | 要求 |
| --- | --- |
| T1 一一对应 | 每个含业务源码的包至少 1 个非空 `*_test.go`；新增源文件要补对应测试文件 |
| T2 命名 | `Test<模块>_<行为>` / `TestUnit_<行为>` / `TestScenario<n>_<场景>` / `TestRule<n>_<规则>`，见名知义 |
| T3 表驱动 | 状态机合法/非法迁移、2 小时取消分界（等于 2h / 小于 2h）、角色权限矩阵用表驱动用例 |
| T4 零外部依赖 | 默认单测不得依赖真实 MySQL/Redis；用 `sqlmock` / `miniredis` / 内存 `StateStore`。真实 DB 集成测试读 `*_TEST_DSN`，未设置自动 `t.Skip` |
| T5 测试隔离 | 并行包不共用同一物理库；名额/时段测试数据每个用例独立 `Reset` |
| T6 竞态 | 涉及并发不变量（名额抢占、取消×核销互斥、重复通知）的测试必须可用 `-race` 跑通 |
| T7 固定命令 | `go test -race -count=1 ./...`（`-count=1` 禁用缓存，避免假绿） |
| T8 覆盖率 | 提交前整体与核心业务包（api/cache/model/service/store/app）均 ≥85%；由覆盖率门禁脚本强制执行 |

## 4. 必测不变量矩阵（每个功能点自己认领）

| 不变量 | 至少要有的一条断言 | 对应规则 |
| --- | --- | --- |
| 名额不超卖 | 并发抢最后 1 个名额，恰好 1 人成功，`occupied_count ≤ 3` | 规则 1 / SC-02 |
| 同一宠物唯一有效预约 | 同一宠物同一时段重复预约被拒，不重复占名额 | 规则 1 |
| 5 分钟占位 | 未付款占位 5 分钟，超时/主动取消后名额精确释放一次 | 规则 2 / SC-02 |
| 支付通知幂等 | 同一 `notify_key` 连续到达 2 次，只确认一次、不重复记收入 | 规则 2 |
| 迟到支付回调 | 已关闭预约收到支付成功 → 登记异常 + 退款，不恢复预约、不恢复名额 | 规则 2 |
| 取消政策分界 | ≥2h 自动受理全额退款；<2h 须原因 + 客服审核；待审核期间名额保持且禁核销 | 规则 3 / SC-03 |
| 取消获准后不可核销 | 名额仅释放一次；退款失败/重试/重复点击均不复活预约 | 规则 4 / SC-03 |
| 核销准入 | 本店 + 已确认 + 无待处理取消申请，三条件任一不满足即拒绝且记录不变 | 规则 5 / SC-04 |
| 取消×核销并发 | 只有一个胜者，状态单一、金额自洽、冲突留痕 | 规则 6 / SC-04 |
| 终态禁入取消 | 已核销/服务中/已完成不能再走取消退款流程 | 规则 6 |
| 未到店 | 时段结束后店长标记并写原因，不自动退款，用户可见 | 规则 7 / SC-05 |
| 收入口径 | 已完成服务收入只认已完成记录；已收款 39600 ≠ 收入 9900 | 规则 8 / SC-05 |

> 复杂不变量先写断言再写实现（`principles.md` 第 2 节 TDD 倾向）；断言可以先红，但闸门必须最终全绿。

## 5. 前端模块的等价要求

当前前端是 `prototype/` 下 HTML+JS 单文件原型，项目未引入 JS 测试框架，**不为了合规硬塞测试框架**。等价要求：

1. 15 个页面中每个写操作（预约、支付、取消、审核、核销、登记开始/完成、标记未到店、时段发布、退款重试、模拟回调）必须在 `general/acceptance.md` 对应场景中有断言。
2. 每个写操作的 `requireRole` 守卫必须被"越权演示"断言覆盖（SC-04 非本店员工操作）。
3. 金额展示 `9900 分 → ¥99.00` 只做格式化，不参与算术；页面不得出现浮点金额比较。
4. 后续落地 React/Vue 时，按 `frontend/code-style.md` 目录新增 `*.test.ts/tsx` 并把新模块纳入模块检查。

## 6. 检查命令

```bash
gofmt -l .                                  # 无输出
go vet ./...                                # 退出码 0
go test -race -count=1 ./...                # 全绿
go test ./... -count=1 -covermode=atomic -coverprofile=coverage.out   # 覆盖率 ≥85%
```

## 7. 与闸门的关系

`feature-gate.md` 的 S2/S3 直接读本文件的模块清单与豁免规则。两者是同一件事的两面：**本文件规定"什么算有单测"，闸门规定"没有就不许往前走"**。
