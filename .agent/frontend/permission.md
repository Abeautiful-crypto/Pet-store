# 05 · 前端权限与越权守卫规范

> 角色权限是本项目的硬约束（5 类角色 / 15 个页面）。本文件规定前端如何落地"权限不能越权"，并与后端接口校验（`backend/constraints.md` 铁律）双保险。
> 页面分配依据：`prototype/宠物门店预约系统-角色页面原型.html` 与 SRS 第 4、11 章。

## 1. 角色与页面映射（页面分配即权限边界）

| 角色 | 分配的页面 | 可发起的操作 | 明确不可做 |
| --- | --- | --- | --- |
| 宠物主人 | U1 时段选择与预约 · U2 订单支付 · U3 取消申请 · U4 我的预约与服务结果 | 选自己的宠物预约、支付 9900 分、取消、查看四种结局 | 为他人宠物预约、编辑档案、查看他人记录、争议退款申诉 |
| 前台及服务人员 | F1 当日接待台 · F2 到店核销 · F3 服务进度登记 | 核销（三条件准入）、登记服务开始/完成 | 核销非本店/未确认/有待处理取消申请的预约、重复记收入 |
| 客服 | C1 取消审核工作台 · C2 退款失败跟进 · C3 处理记录与结果回显 | 批准/拒绝临近取消、退款失败重试、回显结果 | 对已核销/服务中/已完成预约走取消退款流程 |
| 店长 | M1 时段发布 · M2 未到店标记 · M3 日清分类查询 · M4 金额核查 | 发布时段、标记未到店并写原因、五类记录查询、金额核查 | 代客取消、争议退款裁决、把所有已付款计作收入 |
| 模拟支付渠道 | P1 模拟支付控制台 | 返回支付成功/重复通知/迟到回调/退款成功/失败 | 直接修改业务状态、产生真实资金流水 |

> 分配原则：**每个角色只拿完成其业务起点所需的最小页面集**；四个原型模块（用户预约及订单 / 前台接待 / 客服处理 / 店长日清）与角色一一对应。

## 2. `requireRole` 守卫（强制）

- 每个写操作函数第一行：`requireRole(currentRole, allowedRoles, action)`，不通过直接返回 `⛔ 无权访问`，**且声明"未做任何数据改动"**。
- 守卫失败**不回滚任何状态**（本就没改），但要在日志/提示里明确"本次操作被拦截"。
- 后端同样校验：核销需校验 `appointment.store_id == 操作者门店`，买家接口校验 `appointment.user_id == currentUser`；前端守卫是体验层，**不能替代后端**。
- 参考范本已沉淀的真实坑：API 层内部构造"渠道身份"绕过鉴权，导致买家可自助确认退款成功——本项目禁止任何形式的内部身份伪造。

## 3. 数据隔离

- 用户端只读取/操作 `appointment.user_id == currentUser` 且 `pet.owner == currentUser` 的记录；过滤在 api/store 层完成。
- 前台接待台只读**本店当日**预约；跨店数据不展示。
- 角色切换（重新登录）必须清空上一角色的本地状态，避免串数据。
- 所有角色页面顶部"共享记录条"显示同一 `appointment_id`，但**可见字段按角色裁剪**（用户看不到客服审核人，客服看不到收入汇总）。

## 4. 越权演示（SC-04 硬证据）

- 原型固定提供"越权演示"入口：
  1. 非本店员工在 F2 执行核销 → 明确拦截，预约与金额记录不变；
  2. 用户在 U3 对已核销/服务中/已完成预约点取消 → 入口不可见 / 明确拒绝；
  3. 客服在 C1 对已核销预约点批准取消 → 拒绝并给出原因。
- 该演示用于 `general/acceptance.md` SC-04 的"均不能破坏预约和金额记录"断言。

## 5. 禁止项

- 禁止仅靠"前端不显示按钮"实现权限（后端必须独立校验）。
- 禁止把一个角色的写操作接口暴露给其他角色的调用方而不校验。
- 禁止角色切换后残留上一角色数据。
- 禁止页面出现题目明确不做的入口（优惠、会员、排班优化、多店结算、档案编辑、争议退款裁决、未到店自动退款）。
